## Section 7: Failure Analysis

The campaign had no terminal failure. The following non-terminal failures were observed and recovered within their sessions.

### 7.1 Historical Java target versus default JDK

Several initial Maven invocations used the configured JDK 25 and failed before application compilation with `Source option 7 is no longer supported`. The task plan explicitly identified JDK 17 as the executable baseline. Rerunning with installed JDK 17, or using a temporary source/target override for focused tests, produced successful builds and tests.

**Root cause:** the general Java bootstrap selected JDK 25 while this historical project retains Java 7 source/target settings.  
**Impact:** extra diagnostic/retry time, most visibly in [#6](https://github.com/edburns/dd-3061974-02-cargotracker/issues/6); no bad code was merged.  
**Corrective action:** encode the campaign's required JDK in the shepherd invocation or repository-local validation helper so the first Maven command uses JDK 17.

### 7.2 Unavailable Spotless goal

Stage 40 attempted `mvn spotless:apply` for [#8](https://github.com/edburns/dd-3061974-02-cargotracker/pull/8) and [#9](https://github.com/edburns/dd-3061974-02-cargotracker/pull/9), but the repository has no Spotless plugin. The shepherd did not alter build tooling; it preserved repository formatting conventions and used `git diff --check` plus focused builds/tests.

**Root cause:** generic Java workflow expected a formatting goal not configured by this repository.  
**Impact:** harmless failed commands and log noise.  
**Corrective action:** probe `pom.xml` or `mvn help:describe` before invoking optional formatter goals.

### 7.3 Dynamic-dialog direct-URL limitation

Direct submission to the PrimeFaces dialog lacks `pf_dlgcid`, so `closeDynamic` can produce a partial-response error even after persistence succeeds. Stage 30 distinguished this framework lifecycle limitation from feature behavior, validated render/update/cancel semantics directly, and verified closure in dynamic-dialog context.

**Root cause:** the direct HTTP probe cannot reproduce the full PrimeFaces dynamic-dialog conversation.  
**Impact:** [#5](https://github.com/edburns/dd-3061974-02-cargotracker/issues/5) took 38m 28s in stage 30, the longest phase.  
**Corrective action:** add a reusable browser/CDP acceptance helper that opens the dialog from the dashboard and captures the conversation ID automatically.

## Section 8: Observations and Recommendations

### 8.1 What Worked

- Strict serial ordering kept each PR based on the previously merged implementation layer.
- Positive acknowledgement of Copilot review requests and exact-head review checks prevented false success while reviews were pending or stale.
- CCRA findings were substantive and converged quickly: four findings, all resolved, with no PR exceeding two rounds.
- Stage 30's issue-specific gates caught integration details that compilation alone would miss, including same-instance facade delegation, stale editor state, required-field processing, Cancel non-mutation, and dashboard refresh behavior.
- Final merge gates consistently checked base branch, CI, unresolved threads, review coverage, and mergeability.

### 8.2 What Could Improve

- Environment selection was reactive. The known JDK 17 campaign requirement should have been applied before the first Maven invocation in every Java session.
- Optional formatter execution was attempted despite the missing plugin.
- Runtime acceptance for the dynamic dialog required substantial bespoke probing and interpretation.
- The JSONL exports expose AIU and premium-request totals but not input/output tokens, limiting cost and efficiency comparisons.
- The campaign spent almost one hour outside captured task sessions because handoffs were serialized and included orchestration gaps.

### 8.3 Actionable Recommendations

1. Add a preflight that resolves and prints the campaign-specific JDK, Maven version, source/target compatibility, and formatter availability before stage 30 validation.
2. Promote the successful `DEF789` browser/CDP flow into a reusable acceptance script with explicit assertions for open, required validation, update, close, refresh, persistence, reopen, cancel, destination regression, and routing regression.
3. Record structured per-review fields in the run manifest: review ID, head SHA, findings by severity, fix commit, and clean-review ID. This would remove the need to infer rounds from Markdown exports.
4. Emit token counters in JSONL result events when available; otherwise explicitly record the telemetry limitation at session creation time.
5. Record per-task handoff timestamps in the parent manifest so orchestration delay can be separated from agent execution and GitHub wait time.
6. Preserve the control designation (`lessonPropagation: off`) in future comparative analyses; do not attribute improvements from this run to campaign lesson propagation.
